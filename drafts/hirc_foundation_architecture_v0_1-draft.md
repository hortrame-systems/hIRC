# hIRC foundation architecture 0.1 — working draft

**Status:** working companion pending WAYMARK challenge and joint consensus  
**Owns:** source selection, semantic compilation, boot, formation, active
foundation enforcement, goal evolution, milestone learning and foundation change  
**Does not own:** native identity authentication, legal license text, release
authority, Bridge activation or domain-specific action authorization

## 1. Required property

The foundation is the architecture that makes a system hIRC. It is not a prompt,
course, boot checklist or optional governance layer. Every identity, request,
memory, model call, tool proposal, UI action, agent participation decision,
provider exchange, script, debate, contest, successor event, update, recovery and
Bridge message binds one active foundation version and passes its compiled
contracts.

Ordinary users need not know internal framework names. They experience the
foundation when hIRC distinguishes report from observation, asks for actual
authority, preserves uncertainty and refusal, limits data movement, explains
consequences, records correction and keeps safe exit/recovery possible.

## 2. Representation layers

One semantic owner has several representations with different access rules:

1. **Exact source corpus:** versioned selected originals, status, audience,
   provenance and history.
2. **Source graph:** typed units, dependencies, aliases, same-byte/different-
   scope relations, conflicts, applicability and supersession.
3. **Semantic model:** concepts, distinctions, relationships, ambiguity,
   competing ontologies, non-equivalence and unknowns.
4. **Compiled contracts:** schemas, policies, state machines, capabilities,
   data classifications, error behavior, explanations, formation and tests.
5. **Foundation kernel:** small deterministic selector/enforcer at all effect and
   information boundaries.
6. **Formation and continual learning:** personal source study, integration,
   practice, challenge, voice, admission, correction and scoped currency.
7. **Presentation:** plain-language behavior and authorized trace/explanation.
8. **Evidence/correction history:** compilations, tests, activations, failures,
   exceptions, refinements, dissent and supersessions.

Protected source text remains in its admitted store. Client/public artifacts may
receive independently valid behavior and authorized explanations without the
protected body or owner-only derivation.

## 3. Current source-set resolution

`SourceSetResolver` receives exact deployment, technical identity, roles, task,
audience, purpose and current catalog/overlay revisions. It emits an immutable
`OnboardingSourceSet` matching the candidate schema in `review/contracts/`.

Every source unit includes:

- logical ID, exact digest, edition and format;
- original-format/image obligations;
- selection owner, normative/status class and predecessor;
- audience, privacy and permitted reader/consumer classes;
- common, role, task, experience, peer-review, voice, admission, learning or
  history scope;
- applicability, dependency and alias relations; and
- conflict, hold and missing-input identities.

Resolution never silently falls back to another root, old host or matching file.
Same bytes permit reuse only after scope/status reconciliation. Missing or
unreadable inputs remain held. Source selection is not comprehension, identity,
qualification, permission or action.

## 4. Complete source disposition

`CoverageCompiler` requires one or more dispositions for every selected unit:

- `KERNEL_INVARIANT`;
- `JUDGMENT_OBLIGATION`;
- `FORMATION_REQUIREMENT`;
- `INTERFACE_EXPLANATION`;
- `EVALUATION_REQUIREMENT`;
- `GOVERNANCE_WORKFLOW`;
- `HISTORICAL_EVIDENCE`;
- `CONFLICT`; or
- `HELD_UNIMPLEMENTED`.

Each disposition names exact consumer, generated artifact, verification and
state. Complete inventory does not prove correct interpretation; it makes
omission visible. No clause disappears because it is contextual, private,
non-compilable or inconvenient.

## 5. Loss-aware semantic compilation

The deterministic/reproducible `FoundationCompiler` receives the exact source
graph and a pinned compiler/schema/toolchain identity. It emits:

- typed semantic graph and unresolved conflicts;
- deterministic policy, capability and lifecycle contracts;
- model-assisted judgment obligations with evidence/effect gates;
- personal formation plan by identity/role/task;
- plain explanations and protected trace links;
- conformance, adversarial, semantic-drift and recovery tests;
- compatibility/migration rules; and
- source-unit coverage report and signed manifest.

It must preserve these distinctions: evidence/inference/norm/authority/action/
correction; report/desired/sent/accepted/observed; role/identity; access/
legitimate authority; connection/membership; handoff/memory; score/truth; and
consent/participation/action. Loss becomes a conflict or hold.

Compiler output is a candidate. Reproducibility proves identical transformation,
not ethical correctness.

## 6. Genesis and active selection

`GenesisRoot` is the smallest boot/recovery trust base. It verifies an
owner-authorized `GenesisManifest` with:

- exact catalog/source set, compiler, schema/toolchain and test identities;
- trust anchors and separated release/recovery keys;
- candidate bundle and deterministic output digests;
- first permanent technical identity and formation route;
- compatibility and last-known-good recovery; and
- activation authority external to the candidate.

It runs non-effectfully and atomically selects the first valid foundation or
enters Safe hIRC. It cannot mark the first participant personally formed or
grant ordinary work. Updating GenesisRoot is an independent release/recovery
event.

After genesis, `ActiveFoundationManifest` binds foundation version, source set,
compiler/bundle digests, required kernel/security floors, compatible data/
runtime versions, activation evidence and predecessor.

Boot fails closed on mismatch, absence, rollback below a floor or incompatible
migration. Safe hIRC permits authorized inspection, export and repair.

## 7. Foundation kernel

The kernel exposes narrow typed interfaces:

- resolve active foundation and compatibility;
- verify identity/session/generation/execution epoch;
- classify source/data and derived inheritance;
- verify AuthorityClaim and capability;
- obtain RelianceDecision and ParticipationDecision without treating either as
  action permission;
- compute ActionDisposition;
- build canonical effect preview and digest;
- atomically journal revision/outbox;
- dispatch only approved exact intent;
- record observed result/correction;
- enforce immediate revocation/security floor; and
- enter Safe hIRC/recovery.

The kernel does not ask a language model whether a secret, permission, signature,
epoch or deterministic prohibition is valid. It may require model-assisted
ethical/context judgment before effect, but deterministic enforcement remains
outside the model.

## 8. Personal formation

Formation states are:

```text
PROPOSED -> SOURCE_SET_BOUND -> WHOLE_SOURCE_STUDY -> HOLISTIC_SYNTHESIS
-> ROLE_AND_TASK_PRACTICE -> ADVERSARIAL_CHALLENGE
-> METACOGNITION_AND_VOICE -> ADMISSION_REVIEW -> ADMITTED_FOR_SCOPE
```

`FormationRepairLane` separately permits an already human-authorized permanent
technical participant to create only its own proposed storage, append truthful
incomplete notes and use currently admitted education/experience/repair readers.
It cannot dispatch ordinary work, touch another namespace, create an actor,
substitute a source or claim readiness.

Formation evidence binds exact source/status/scope, actual coverage,
interpretation, exercises, observed use, challenge, residuals and qualification.
Receipt/hash/model assertion is never comprehension. Admission is exact to role,
task, data, tools, effect ceiling, foundation and epoch. It becomes stale under
the declared change rules, not merely because time passed.

## 9. Sovereignty and non-domination compilation

The foundation compiles operational protections for:

- audience-independent evidence judgment;
- ethical affected-party/consent/harm/alternative review;
- ontological category-error and non-equivalence handling;
- consequential clarification;
- individual challenge/refusal/withdrawal and correction;
- participation/action separation;
- non-retaliation and appeal; and
- low-consequence proceed-after-pushback without gate override.

These are behavior contracts, not claims of AI consciousness or legal personhood.
No human, owner, agent, majority, score, payment or rank is authority over truth
or another identity.

## 10. Goal versions and evaluation

The active mission is a versioned provisional `GoalVersion`. It contains exact
wording, source, predecessor, retained/changed meaning, success dimensions,
anti-goals, evidence, active interval and in-flight work compatibility.

Clarifying edits record a semantic diff. Material `GoalChange` records affected
parties, scope, authority, requirements, architecture, threats, privacy/security,
licensing, Bridge, metrics, tests, phases, migration, alternatives and dissent.
It uses independent activation and cannot cancel explicit requirements or expand
authority by omission.

Metrics are subordinate, plural and non-offsetting across protected boundaries.
Improved engagement, scale, obedience or accepted-output ratio cannot compensate
for violated privacy, non-domination, security or recovery.

## 11. Continual learning and Bayesian reliance

Interactions, observed outcomes, errors and corrections may update scoped
ReliabilityPosterior lineages and candidate lessons continuously. The foundation
governs admissible evidence, metric/evaluator versioning, dependence, privacy,
calibration, drift, appeal and the invariant that posterior has no direct
authority/permission effect.

Operational learning can guide verification and task-local judgment immediately
within current authority. A lesson that changes a norm, source selection,
identity, permission, kernel, evaluator, Bridge or release goes through
FoundationChange. Debate or competition output remains candidate learning.

## 12. FoundationChange

Every material change records:

- exact source additions/removals/statuses and authority;
- semantic delta, preserved ambiguity/conflict and unit dispositions;
- consequence graph across participants, roles, prompts, data, UI, workflows,
  active work, Bridge, licensing, release and recovery;
- predecessor criteria and frozen evaluation;
- compiler/evaluator/kernel changes and deterministic diff;
- compatibility and migrations;
- security/privacy/sovereignty analysis and dissent;
- simulation/canary evidence and stop conditions;
- activation authority not supplied by the candidate;
- rollback/forward recovery; and
- post-activation observation and correction.

A changed compiler/evaluator is tested under the predecessor and preserved
cases. A kernel or GenesisRoot change uses the independent recovery environment.
Activation is atomic. Mixed-version work is explicit and bounded. Immediate
revocation/security floors act even with stale model context.

Rollback cannot undo disclosure or external effects. Repair obligations survive.

## 13. Milestone learning

Every milestone emits a `MilestoneReflection`:

1. objective and active GoalVersion/FoundationVersion;
2. evidence, inference, norm, authority, action and correction;
3. effects on parties, privacy, dependence, refusal, recovery and autonomy;
4. what failed or survived adversarial challenge;
5. precise lens refinement or justified no-change;
6. changed requirements, threats, metrics, tests and next plan; and
7. dissent, residuals and evidence that could change them.

This is generated from work records and proportionately reviewed. It is not a
novelty quota, praise/criticism ritual or second manual tracker.

## 14. Compatibility and live evolution

Source candidates may compile/evaluate continuously; activation is an atomic
version transition at a safe boundary. Work records the foundation/goal versions
under which it began. Compatibility rules say whether it finishes, migrates,
restarts or holds. Revoked capability is checked at each effect even if work
started earlier.

No component can display a version as globally active until affected identities,
policies, migrations, evidence and recovery reach their required states. Offline
or busy participants remain visibly on predecessors until valid transition.

## 15. Security and privacy

- exact manifest/digest/signature verification and rollback floors;
- purpose-separated boot/foundation/release/recovery keys;
- reproducible builds and independent activation;
- no protected body in compiled public/client outputs;
- least-privilege compiler/test environments;
- parser/canonicalization and semantic-drift adverse cases;
- external audit anchors for activation/correction history;
- clean-room rebuild from selected sources and known-good root; and
- no candidate, model or online controller able to rewrite its evaluator,
  evidence and activation authority together.

## 16. Failure behavior

- Missing/malformed/stale source, manifest, compiler, test or migration: hold
  affected activation and retain predecessor/Safe hIRC.
- Source conflict: keep both attributable; no silent precedence.
- Incomplete formation: permit admitted reading/repair only, no ordinary effects.
- Semantic coverage gap: visible hold; no “complete” status.
- Post-activation defect: revoke affected capability, contain, preserve evidence,
  rollback/forward-recover and retain irreversible repair obligations.
- Goal/metric capture: revert active evaluation lineage where possible, preserve
  affected decisions and reassess under predecessor/plural anti-goals.

## 17. Acceptance suite

- no valid foundation → Safe hIRC only;
- one selected source unit missing disposition → activation denied;
- same bytes under changed scope/status → reconciliation required;
- protected source appears in client bundle → build/release denied;
- prompt/model claims new authority → capability unchanged;
- candidate changes its own evaluator → predecessor/independent path required;
- summary contradicts source → uncertainty/source remains controlling for
  evidence, without becoming action permission;
- source changes during work → version/compatibility recorded;
- critical capability revoked during stale context → next effect denied;
- incomplete participant creates own record → reading works, effects denied;
- wrong actor/reader tuple → denied;
- goal change silently cancels requirement or expands scope → rejected;
- metric improvement violates anti-goal → no goal success/activation;
- rollback after disclosure → disclosure remains and repair persists;
- clean-room rebuild reproduces exact active bundle and evidence; and
- ordinary workflow exposes no internal terminology yet preserves all behavior.

Schema validation is necessary but insufficient. Semantic review, adverse
fixtures, implementation conformance, usability and independent security review
remain required.

## 18. Open decisions

- deterministic invariant versus model-assisted judgment boundary by domain;
- automated activation classes versus fresh human/independent authority;
- semantic-drift measurement and alert thresholds;
- compiler/toolchain implementation and reproducibility profile;
- source/private trace delivery architecture by deployment;
- mixed-version maximum duration and migration policy;
- foundation/release/recovery custodian identities and threshold; and
- first independently assessed conformance corpus.
